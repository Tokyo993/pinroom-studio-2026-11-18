# PinStudio
## Опис реалізації тестового завдання

PinStudio — мобільний вебзастосунок за мотивами основних сценаріїв Pinterest. Користувач шукає зображення, переглядає піни й збирає особисті колекції. Додана функція — фотостудія всередині застосунку: кадрування, налаштування кольору, фільтри, текст та експорт PNG. Інтерфейс оформлено в темній темі з фіолетовими акцентами за наданим референсом.

Документ описує реалізацію, запуск, захист даних, роботу AI-агентів та результати перевірок станом на 19 листопада 2026 року. Це навчальний проєкт, не офіційний продукт Pinterest або Adobe.

### Матеріали для перевірки

Застосунок: https://pinroom-studio-nov18-nk.toky0993.chatgpt.site

Репозиторій: https://github.com/Tokyo993/pinroom-studio-2026-11-18

Код та інструкція запуску — у README репозиторію. Окремий запис актуального застосунку — pinstudio-auth-demo.webm. Детальний сценарій демонстрації — docs/DEMO-SCRIPT.md.

Сайт і репозиторій приватні. Перед здачею власник має надати перевіряльнику доступ. Вхід на опублікованому сайті відбувається через власний дозволений акаунт ChatGPT; спільного тестового пароля немає.

### Відповідність функціональному обсягу

| Екран | Основний сценарій |
| --- | --- |
| Стрічка та пошук | Категорії, пошук, завантаження наступної порції зображень |
| Деталі піна | Автор, ліцензія, джерело, збереження та перехід у редактор |

Пошук працює на екрані стрічки. Вхід, профіль та вибір колекції відкриваються в діалогах, тому основний інтерфейс залишається в межах п’яти сторінок.

## Інтеграція зовнішнього API

Дані надходять із Wikimedia Commons через MediaWiki Action API. API Pinterest не використовується: відтворено сценарії продукту, а фотографії та метадані отримуються з відкритого джерела. API-ключ не потрібний.

Модуль public/api.js виконує пошук, нормалізує назви, авторство, ліцензії, посилання та розміри зображень. Запити виконуються з credentials omit. Є скасування попереднього пошуку, тайм-аут, кеш у пам’яті та повідомлення про мережеві помилки. Наступні результати завантажуються за зміщенням, повернутим API.

Метадані перетворюються на текст. URL перевіряються за протоколом і дозволеними доменами; небезпечні адреси й непридатні записи відкидаються. У піні зберігаються джерело, автор та ліцензія. Експорт зображення Wikimedia містить смугу атрибуції й позначення змін. Wikimedia отримує пошуковий запит та IP-адресу відвідувача.

## Нова функція фотостудії

Редактор працює на Canvas у браузері. Він підтримує оригінальний кадр, 1:1, 4:5, 16:9 і 9:16; масштаб і зміщення кадру; поворот на 90° та віддзеркалення. Користувач регулює яскравість, контраст і насиченість, застосовує теплий, холодний, чорно-білий або сепія-фільтр.

Один текстовий шар має налаштування змісту, кольору, розміру й позиції. Історія зберігає до 40 станів, підтримує скасування та повтор. Кнопка порівняння показує оригінал. Збереження створює окремий пін і не замінює початкове зображення.

Можна відкрити власний JPG, PNG або WebP до 15 МиБ. Робоча довга сторона обмежена 1600 px; атрибуція може додати висоту експорту. Збережений результат має бути до 10 МиБ. Редагування відбувається локально; лише після збереження результат надсилається до особистого серверного сховища.

### Технології

Клієнт написаний на HTML, CSS і JavaScript ES modules. Vinext та Vite збирають Cloudflare Worker. D1 зберігає колекції та метадані файлів, R2 — приватні зображення. Drizzle описує схему й генерує міграції. Для тестів використано node:test; для перевірки інтерфейсу — Chrome та Playwright.

## Авторизація та захист даних

На опублікованому сайті вхід і вихід обслуговує платформа ChatGPT/Sites. Сервер читає перевірену ідентичність через getChatGPTUser з довірених заголовків dispatch. Стабільний user ID є ключем власника; email та ім’я використовуються лише для відображення. Застосунок не створює власних паролів і не зберігає токени в localStorage.

Кожне читання або зміну особистих даних сервер прив’язує до автентифікованого власника. Поля owner_id із браузера не визначають доступ. Приватне зображення видається тільки через /api/assets/:id після перевірки власника в D1; відкритих посилань на R2 немає. Відсутні та чужі файли повертають однакову відповідь 404.

### Захист під час зміни даних

- Записи потребують точного збігу Origin з адресою застосунку.
- Запити колекцій і завантаження файлів містять очікуваний ID акаунта. Сервер лише порівнює його з довіреною ідентичністю. Це зупиняє збереження даних зі старої вкладки після зміни акаунта.
- Кожна бібліотека користувача має ревізію. Атомарний SQL-запис допускає лише актуальну ревізію; конкурентний запис повертає 409.
- Перевіряються структура JSON, ідентифікатори, розміри, приватні посилання, MIME та сигнатура зображення. Ліміти діють і для потокового тіла без Content-Length.
- Приватні відповіді мають no-store та nosniff. Дані екрануються в HTML; CSP обмежує джерела скриптів, зображень і мережевих запитів. Помилки сервера не розкривають SQL або ключі об’єктів.

Старі колекції IndexedDB імпортуються лише за явним підтвердженням користувача. Після успішного перенесення можна видалити локальну копію. Після виходу поточна вкладка очищає дані акаунта з пам’яті; нові приватні запити потребують входу.

### Межі моделі безпеки

Захист розрахований на довірений Sites dispatch. Пряме публічне розміщення Worker без перевіреного шлюзу ідентичності потребує іншого механізму автентифікації. Локальний dev-вхід — лише імітація для localhost, не production-авторизація. Адміністратор хостингу має технічний доступ до сховища; наскрізне шифрування не реалізоване. На спільному пристрої потрібно виходити з акаунта й закривати відкриті вкладки.

## AI агенти та пайплайн

У роботі над проєктом використано чотири логічні Codex-агенти: координатор та три спеціалізовані агенти. Назви нижче — фактичні назви завдань у середовищі. Точна модель кожного історичного запуску не зафіксована, тому однакова версія моделі для всіх не заявляється.

| Агент | Завдання та налаштування |
| --- | --- |
| Координатор | Архітектура, інтерфейс, інтеграція, перевірки в браузері, документація та публікація |
| api_tests | API, нормалізація та тести; пізніше серверний контракт авторизації, D1 і R2 |
| editor_core | Геометрія Canvas, історія змін і тести чистих функцій; документація попередньої версії |
| auth_review | Незалежний огляд авторизації; виправлення зміни акаунта між вкладками й регресійні тести |

Агентам передавалися конкретні контракти функцій і межі файлів. API та ядро редактора розроблялися паралельно. Для огляду авторизації спочатку було встановлено режим без редагування; після підтвердження дефекту агент отримав право змінити лише серверний модуль, клієнт сховища та відповідні тести. Координатор окремо інтегрував результат.

Пайплайн: декомпозиція → реалізація модулів → інтеграція → незалежний огляд → синтаксичні та автоматичні тести → збірка → браузерні сценарії → фіксація коду → публікація. GitHub Actions повторює синтаксичні перевірки, тести, встановлення залежностей та production-збірку на Node.js 24. AI-агенти використовувалися для розробки й перевірки; сам CI виконує детерміновані команди.

### Як перевіряли результат AI

Звіт агента не вважався доказом працездатності. Код переглядався та запускався, результати перевірялися тестами й фактичними сценаріями в Chrome. Перевірено реальне завантаження Wikimedia, зміну пікселів Canvas, відновлення після перезавантаження, збереження похідного піна та блокування приватних даних після виходу.

Незалежний огляд виявив дефект: стара вкладка могла зберегти колекцію в новий акаунт після перемикання користувача. Додано перевірку очікуваного акаунта на сервері та чотири регресійні тести, зокрема перемикання під час асинхронного завантаження. Після виправлення тести й браузерні сценарії повторено.

## Тести та результати

Останній локальний прогін: 50 автоматичних тестів пройшли, 0 помилок. Синтаксична перевірка та production-збірка успішні. Окремо пройшли 12 браузерних перевірок із реальним API; необроблених JavaScript-помилок не виявлено. Підтвердження збережено в docs/auth-browser-report.json та файлах tests.

| Група | Кількість | Чому перевіряли |
| --- | --- | --- |
| Wikimedia API | 11 | Недовірені метадані, URL, помилки мережі, скасування та пагінація |
| Ядро редактора | 11 | Геометрія кадру, межі значень, розміри експорту, незмінність історії |
| Операції колекцій | 4 | Валідація назв, повторне збереження, видалення без втрати спільних посилань |
| Авторизація та сховище | 24 | Ізоляція акаунтів, приватні файли, CSRF, конфлікти, ліміти та зміна сесії |

Чисті модулі перевіряються юніт-тестами. Серверні тести викликають реальний обробник з SQLite у пам’яті через адаптер D1 та тестовим R2. Це додаткові інтеграційні перевірки сервісного шару, а не перевірка самого провайдера ChatGPT. Два різні користувачі в тестах не можуть прочитати чи перезаписати дані один одного.

Браузерний прогін охоплює заборону доступу гостю, локальний вхід, стрічку, збереження після перезавантаження, пошук з колекції, фільтр і скасування, квадратний кадр, PNG, окреме збереження результату, приватне зображення власника, ширину 320 px та вихід. Перевірку відсутності необроблених помилок скрипт рахує окремим пунктом.

### Що перевірки не доводять

Локальний браузер використовує тестовий вхід. Повний production-сценарій OAuth із двома реальними ChatGPT-акаунтами не автоматизовано. Успішний деплой підтверджує публікацію, але не замінює перевірку доступу конкретного перевіряльника. Навантажувальні тести та окремий зовнішній аудит безпеки не проводилися.

### Повторення перевірок

У корені репозиторію виконайте npm ci, потім npm run check, npm test і npm run build. Браузерний сценарій запускається командою node scripts/browser-check.mjs за наявності Chrome, Playwright і dev-сервера на порту 4173. Детальні команди та змінні середовища наведено в README.

## Запуск та здача

Для локального запуску потрібні Node.js 24 LTS, npm та інтернет. У корені проєкту послідовно виконайте команди нижче. API-ключі або власний обліковий запис Cloudflare для локального запуску не потрібні.

```sh
npm ci
npm run setup
npm run dev -- --port 4173
```

Відкрийте http://127.0.0.1:4173/. У профілі натисніть «Войти через ChatGPT». Лише в dev-режимі створюється тестова сесія Seedy / seedy@sites.test без пароля. Локальні D1 і R2 зберігаються в .wrangler/state та відокремлені від сервера. Повторне застосування міграцій перевірено: вже виконані міграції пропускаються.

На опублікованому сайті працює справжній ChatGPT-вхід. Після надання доступу перевіряльник може знайти пін, створити колекцію, перезавантажити сторінку, відредагувати зображення, зберегти окрему версію, завантажити PNG та вийти.

### Що ще потрібно перед відправленням

- Надати перевіряльнику доступ до приватного сайту та репозиторію і перевірити його власний вхід.
- Додати до фінального відео короткий вступ із доступним оригінальним Pinterest. Запис pinstudio-auth-demo.webm демонструє реалізований застосунок і редактор; повноцінного вступу по оригіналу в ньому немає.
- Перевірити доступність відеофайлу для адресата. Не передавати особисті паролі чи сесійні токени.

## Час та обмеження

Робота виконувалася 18–19 листопада 2026 року з перервами. Для першої реалізації зафіксовано контрольний проміжок приблизно 20 хвилин, після чого окремо виконувалися публікація, редизайн, авторизація й документація. Безперервний облік активного часу не вівся; достовірна загальна кількість людино-годин не відновлена. Календарний проміжок та паралельний час агентів не підсумовуються як активна робота.

Рішення обмежене 100 колекціями, 1000 пінами та JSON-запитом до 1 МиБ. Немає спільних дошок, персональних рекомендацій, PSD, масок або кистей. Синхронізація відбувається під час читання та збереження, без live-оновлень. При конфлікті потрібно оновити колекції та повторити дію.

Невикористані файли R2 після видалення піна або невдалого збереження поки не очищаються автоматично; квоти й очищення сховища потребують окремого доопрацювання. Доступність зовнішніх зображень залежить від Wikimedia. Ці межі зазначені відкрито й не приховані демонстраційними даними.
